# IP / TCP / HTTP Header Boundary Analysis

## 目的

前回取得したHTTP通信の16進数データを使用し、

- IPv4ヘッダ
- TCPヘッダ
- HTTPデータ

がパケット内のどこに格納されているのかを、
実際のバイト列から確認する。

tcpdumpが表示するIPアドレスやポート番号が、
実際のパケット内のどのデータから読み取られているのかを理解する。

## 環境

- Kali Linux
  - IPv4: `192.168.10.129`

- Ubuntu Server 24.04 LTS
  - IPv4: `192.168.10.128`

- VMware Workstation
- Host-only Network
  - `192.168.10.0/24`

今回の解析には、
前回保存したHTTP GETリクエストのキャプチャを使用した。

## 1. 解析対象のパケット

解析したHTTPリクエストは以下の通信である。

    192.168.10.129:42266
        ↓
    192.168.10.128:80

HTTPデータ:

    GET / HTTP/1.1
    Host: 192.168.10.128
    User-Agent: curl/8.20.0
    Accept: */*

tcpdumpでは、
同じパケットを16進数とASCIIでも確認できた。

    0x0000: 4500 0082 9043 4000 4006 13e1 c0a8 0a81
    0x0010: c0a8 0a80 a51a 0050 8f6a bc6a 7406 7ff9
    0x0020: 8018 00fb f134 0000 0101 080a 2ff9 5a16
    0x0030: 0fc9 ff62 4745 5420 2f20 4854 5450 2f31
    0x0040: 2e31 0d0a 486f 7374 3a20 3139 322e 3136
    ...

## 2. 16進数表示の読み方

tcpdumpの表示では、

    4500

のような16進数4桁のまとまりは2バイトを表す。

1バイトは8bitであり、
16進数では2桁で表現される。

したがって、

    45 = 1 byte
    00 = 1 byte

    4500 = 2 bytes

となる。

1行にはこの2バイトのまとまりが8個あるため、

    2 bytes × 8 = 16 bytes

となる。

左側の、

    0x0000
    0x0010
    0x0020
    0x0030

は、
パケット先頭からのバイト位置を16進数で表したオフセットである。

    0x0000 = 0 byte
    0x0010 = 16 bytes
    0x0020 = 32 bytes
    0x0030 = 48 bytes

## 3. IPv4ヘッダの開始

パケットの先頭は、

    45

から始まっている。

この1バイトは、

    4 | 5

と分けて読むことができる。

最初の `4` は、

    IP Version = 4

を表す。

つまりIPv4である。

次の `5` はIHL
（Internet Header Length）を表す。

IHLは4バイト単位なので、

    5 × 4 bytes
    = 20 bytes

となる。

したがって、
このパケットのIPv4ヘッダは20バイトである。

## 4. IPv4ヘッダの範囲

最初の1行は16バイトある。

    0x0000:
    45 00 00 82 90 43 40 00 40 06 13 e1 c0 a8 0a 81

残り4バイトは次の行の、

    0x0010:
    c0 a8 0a 80

である。

つまりIPv4ヘッダは、

    45 00 00 82 90 43 40 00
    40 06 13 e1 c0 a8 0a 81
    c0 a8 0a 80

までである。

合計すると、

    16 bytes + 4 bytes
    = 20 bytes

となる。

境界は以下のようになる。

    0x0010: c0 a8 0a 80 | a5 1a 00 50 ...
                         ↑
                     IPここまで

`a5 1a` からTCPヘッダが開始する。

## 5. IPv4ヘッダ内のIPアドレス

IPv4ヘッダ後半には、

    c0 a8 0a 81

という4バイトがある。

16進数を10進数に変換すると、

    c0 = 192
    a8 = 168
    0a = 10
    81 = 129

となるため、

    192.168.10.129

を表している。

これはKali Linuxの送信元IPアドレスである。

続く、

    c0 a8 0a 80

は、

    192.168.10.128

となり、
Ubuntu Serverの宛先IPアドレスである。

つまり、

    c0 a8 0a 81
    ↓
    192.168.10.129

    c0 a8 0a 80
    ↓
    192.168.10.128

という対応を確認できた。

## 6. IP Protocolフィールド

IPv4ヘッダ内には、

    06

という値が含まれている。

IPv4のProtocolフィールドにおいて、

    06 = TCP

を表す。

つまりIPv4ヘッダ自身が、

    このIPパケットのペイロードはTCP

であることを示している。

## 7. TCPヘッダの開始

IPv4ヘッダは20バイトなので、

    0x0014

からTCPヘッダが開始する。

実際のデータでは、

    a5 1a 00 50

から始まる。

TCPヘッダの最初の2バイト、

    a5 1a

は送信元ポート番号である。

10進数にすると、

    42266

となる。

続く、

    00 50

は宛先ポート番号である。

    0x0050 = 80

なので、

    42266 → 80

というTCP通信であることが分かる。

これはtcpdumpの、

    192.168.10.129.42266 > 192.168.10.128.80

という表示と一致する。

## 8. TCPヘッダの長さ

TCP部分には、

    80 18

という値が確認できる。

先頭の `8` はTCPのData Offsetを表している。

Data Offsetも4バイト単位なので、

    8 × 4 bytes
    = 32 bytes

となる。

今回のTCPヘッダは32バイトである。

TCPの基本ヘッダは20バイトだが、
今回はTimestampなどのTCPオプションが含まれているため、
32バイトになっている。

tcpdumpでも、

    options [nop,nop,TS ...]

と表示されていた。

## 9. HTTPデータの開始位置

今回のヘッダ長は、

    IPv4 Header = 20 bytes
    TCP Header  = 32 bytes

である。

合計すると、

    20 + 32
    = 52 bytes

となる。

52を16進数にすると、

    0x34

である。

したがって、

    0x0034

からTCPのペイロード、
つまりHTTPデータが開始する。

実際の16進数を見ると、

    0x0030: 0fc9 ff62 4745 5420 ...

の、

    47 45 54 20

が0x0034から始まっている。

## 10. HTTP文字列を16進数から確認

16進数、

    47 45 54 20

をASCIIとして読むと、

    47 = G
    45 = E
    54 = T
    20 = Space

となる。

そのため、

    GET 

という文字列になる。

続けて読むと、

    47 45 54 20 2f 20 48 54 54 50 2f 31 2e 31

は、

    GET / HTTP/1.1

となる。

つまり、
tcpdumpが表示しているHTTPリクエストは、
実際にこのバイト列としてネットワーク上を流れている。

## 11. パケット全体の構造

今回のパケットは以下のように整理できる。

    IPv4 Header
    20 bytes
    0x0000 ～ 0x0013

            ↓

    TCP Header
    32 bytes
    0x0014 ～ 0x0033

            ↓

    HTTP Data
    0x0034 ～

    GET / HTTP/1.1
    Host: 192.168.10.128
    User-Agent: curl/8.20.0
    Accept: */*

概念的には、

    IP Packet
    ├── IPv4 Header
    │
    └── TCP Segment
        ├── TCP Header
        │
        └── HTTP Data

という入れ子構造になっている。

## 12. tcpdumpが情報を表示できる理由

tcpdumpは、

    192.168.10.129
    192.168.10.128
    42266
    80
    GET / HTTP/1.1

といった情報を、
別の場所から取得しているわけではない。

実際にネットワークを流れているバイト列を、

- IPv4
- TCP
- HTTP

それぞれのプロトコル仕様に従って解析し、
人間が読みやすい形式へ変換して表示している。

今回、
16進数データとtcpdumpの表示内容が
実際に一致することを確認できた。

## 学んだこと

- 16進数2桁が1バイトを表す
- tcpdumpの1行には16バイト分のデータが表示される
- `0x0010` などはパケット先頭からのオフセットを表す
- IPv4ヘッダの先頭 `45` からIP VersionとIHLを読み取れる
- IHLからIPv4ヘッダが20バイトであることを確認できる
- IPv4ヘッダ内から送信元・宛先IPアドレスを読み取れる
- IPv4のProtocol値 `06` はTCPを表す
- IPv4ヘッダ直後からTCPヘッダが開始する
- TCPヘッダから送信元・宛先ポート番号を読み取れる
- TCP Data OffsetからTCPヘッダ長を確認できる
- 今回のTCPヘッダはオプションを含むため32バイトだった
- IPヘッダ20バイト + TCPヘッダ32バイトの後からHTTPデータが始まる
- `47 45 54 20` がASCIIでは `GET ` を表す
- tcpdumpは実際のバイト列をプロトコル仕様に従って解析している
