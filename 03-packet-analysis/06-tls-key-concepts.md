# TLS Certificate and Key Concepts

## 目的

これまでのHTTPS / TLS通信の観察結果をもとに、

- 証明書
- 公開鍵
- 秘密鍵
- 鍵交換
- 共通鍵

の役割と関係を整理する。

今回の記録では、
実際のパケットキャプチャで確認できた事実と、
TLSの一般的な仕組みを分けて理解する。

## 2. 証明書とは

TLSで使用される証明書は、
サーバーの識別情報や公開鍵などを含むデータである。

今回のラボでは、
OpenSSLを使用して自己署名証明書を作成した。

    cert.pem

この証明書には、

- 公開鍵
- サーバーに関する識別情報
- 証明書の有効期間
- 署名情報

などが含まれる。

通常のWebサイトでは、
CA（Certificate Authority / 認証局）が証明書へ署名する。

クライアントはその署名を確認することで、

    この証明書は信頼できる認証局によって保証されているか

を判断する。

今回使用した証明書は自己署名証明書であるため、
通常のCAによる保証は存在しない。

そのためcurlでは、

    curl -k

を使用し、
証明書の信頼性チェックを省略した。

ただし、
`-k` を使用してもTLS暗号化自体は有効である。

## 3. 公開鍵と秘密鍵

今回作成したファイルは、

    cert.pem
    key.pem

である。

### cert.pem

    公開してよい情報

証明書の中には公開鍵が含まれる。

クライアントは証明書を受け取り、
サーバーの認証などに利用する。

### key.pem

    サーバーだけが保持する秘密情報

秘密鍵は外部へ公開してはいけない。

公開鍵と秘密鍵は対応しており、
サーバーが正しい秘密鍵を保持していることが
TLS認証の重要な要素となる。

整理すると、

    cert.pem
    → 公開鍵を含む
    → クライアントへ送信可能

    key.pem
    → 秘密鍵
    → サーバーのみで保持

となる。

## 4. 証明書の目的

証明書の大きな目的は、

    この公開鍵は本当にこのサーバーのものか

を確認することである。

つまり証明書は、
単純に暗号化用の鍵を配布するだけのファイルではない。

サーバーの身元と公開鍵を結び付ける役割を持つ。

概念的には、

    サーバー
        ↓
    証明書
        ↓
    公開鍵
        ↓
    クライアントが検証

という流れになる。

## 5. 公開鍵でHTTPデータをすべて暗号化するわけではない

HTTPSでは、

    GET / HTTP/1.1
    HTML
    JSON
    画像データ

など大量のデータを送受信する。

これらすべてを公開鍵暗号だけで処理するのは、
一般に処理コストが高い。

そのためTLSでは、

    公開鍵暗号・証明書
    → 認証や安全な鍵確立に利用

    共通鍵暗号
    → 実際の通信データ暗号化に利用

という役割分担を行う。

## 6. 鍵交換

TLS通信では、
クライアントとサーバーが
暗号化通信に必要な秘密情報を安全に確立する。

今回のClientHelloでは、

    supported_groups

を実際に確認した。

これは、
クライアントが対応可能な鍵交換関連のグループ候補を
サーバーへ提示するための情報である。

TLS 1.3では、
クライアントとサーバーが鍵交換に必要な情報を使用し、
双方で共通の秘密を計算する。

重要なのは、

    共通鍵そのものを
    ネットワーク上へそのまま送信するわけではない

という点である。

## 7. 共通鍵

鍵交換が成功すると、
クライアントとサーバーは
同じ秘密情報から暗号化用の鍵を導出できる。

この鍵を利用して、

    Application Data

を暗号化する。

今回の実験では、
tshark上で、

    TLSv1.3 Application Data

が双方向に流れていることを確認した。

その内部には、

    GET / HTTP/1.1

や、

    <h1>HTTPS TEST</h1>

などのHTTPデータが含まれている。

しかし、
TLSによって暗号化されているため、
パケットキャプチャからそのまま読むことはできなかった。

## 8. なぜ共通鍵暗号を使うのか

共通鍵暗号は、
大量データを高速に暗号化することに向いている。

そのため、

    TLSハンドシェイク
        ↓
    認証
        ↓
    鍵交換
        ↓
    暗号化用の鍵を導出
        ↓
    共通鍵暗号でApplication Dataを保護

という流れになる。

概念的には、

    公開鍵暗号
    → 安全な通信開始のため

    共通鍵暗号
    → 実際の大量データ通信のため

という役割分担である。

## 9. 今回のTLS通信との対応

これまでの観察結果を、
鍵の観点から整理すると以下のようになる。

    Kali Linux
        ↓
    ClientHello
        ↓
    TLSバージョン候補
    Cipher Suites
    supported_groups
    ALPN
        ↓
    Ubuntu Server
        ↓
    ServerHello
        ↓
    利用するTLS設定を選択
        ↓
    サーバー認証
    証明書 / 公開鍵 / 秘密鍵が関係
        ↓
    鍵交換
        ↓
    双方が暗号化用の鍵を導出
        ↓
    Application Data
        ↓
    HTTPデータを暗号化

## 10. 実際に確認した事実と概念の区別

今回のパケットキャプチャで
実際に確認したものは、

    ClientHello
    ServerHello
    Cipher Suites
    supported_groups
    ALPN
    supported_versions
    Application Data

である。

一方、

    証明書によるサーバー認証
    鍵交換
    共通秘密の計算
    共通鍵の導出

については、
TLSの一般的な仕組みとして整理した。

パケット解析では、

    実際に観測できたこと

と、

    プロトコル仕様上そう動作すること

を混同しないことが重要である。

## 学んだこと

- 証明書には公開鍵やサーバー識別情報などが含まれる
- 秘密鍵はサーバーのみで保持する
- 証明書はサーバーの身元と公開鍵を結び付ける
- 自己署名証明書には通常のCAによる保証がない
- `curl -k` は証明書検証を省略するがTLS暗号化は維持される
- HTTPSのHTTPデータを公開鍵で直接すべて暗号化するわけではない
- 公開鍵暗号と共通鍵暗号には役割分担がある
- 鍵交換によって双方が安全に暗号化用の秘密を確立する
- 共通鍵そのものをネットワーク上へ直接送るわけではない
- Application Dataは共通鍵暗号によって保護される
- 実際の観測結果とTLSの一般的な仕組みを分けて考える必要がある
